Usage guide / operator view

Captain’s Chair in use

Start with a job in plain language. The Chair turns it into a governed run, chooses named tools, pauses at the right approval boundary, and returns both the result and the proof behind it.

Start here

You ask for the outcome. The system exposes the consequential choices.

BLUF

You should not have to orchestrate models, hunt for context, or remember which connector can do what. State the job, review the run plan when it matters, approve external or irreversible effects, and receive an artifact with a traceable receipt.

The Chair is a control plane around the tools you already use. It is not another chat window. Claude Code, Codex CLI, Hermes, notebooks, and local models remain useful surfaces; the Chair gives their work one managed record.

Produce a client deliverableResearch, evaluate, render, accept, deliver. Act on inbound workEmail, calendar, CRM, and task follow-up. Build and ship softwareWorktree, tests, review, PR, release evidence. Keep analysis localDuckDB, Jupyter, Ollama, or LM Studio.

High-level system design

Named tools only

Read left to right. The operator can enter through several familiar products, but authority and evidence converge in the same Chair services. The product list is an integration target set, not a mandate to install every item.

Important distinction. Hermes is the named executive-assistant lane for bounded context and task intake. It is not the coding or execution backend. Claude Code and Codex CLI remain direct work surfaces; cc-kernel owns the governed run.

Reality boundary

What exists, what is designed, and what is optional

Running now

  • This verified documentation site
  • Interactive console mockups are illustrative; private feedback uses the authenticated workflow.
  • The existing Captain’s Chair architecture explainer

Designed, not yet implemented

  • chair MCP server and cc CLI
  • cc-kernel, workers, policy, memory, proof, and artifact services
  • The named functions and eight governed flows on this page

Concrete options, not commitments

  • Gmail or Outlook; Google or Outlook Calendar
  • HubSpot or Salesforce; Linear or Jira
  • Lima, Colima, or Docker; Pandoc or LibreOffice
  • Temporal, PostgreSQL, and remote object storage if later scale earns them

This page is a usage specification and design aid. It does not claim that the Captain’s Chair runtime, connectors, or console are already installed. The detailed rationale and failure semantics live in the technical architecture explainer.
